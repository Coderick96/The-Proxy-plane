Code review: the migration compares `pg_get_expr` output against known CHECK expressions generated by the same engine. It drops only recognized 10/15 entitlement constraints, retaining kind/range checks, and adds the compatible 10/15 check. No balance rows are rewritten. Unknown constraints raise an exception inside the encompassing transaction; there is no broad CHECK removal. Allowance reads remain owner-filtered with RLS; mutations and privileged functions retain explicit server-role grants/revokes.

Operational limitations: `ACCESS EXCLUSIVE` lock serializes setup with allowance reads/writes and can block production traffic. Any eventual approved migration needs a maintenance window or bounded lock timeout and rollback planning. Different PostgreSQL versions, casts, reordered expressions, custom constraints or additional historical variants may not match canonical expressions and will safely abort; passing PGlite is not proof that every hosted schema variant will migrate. A disposable real PostgreSQL/staging clone should verify exact hosted definitions before any explicitly approved write. No migration was applied to the real-data project.
